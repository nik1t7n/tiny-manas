# Tiny Manas: план изучения и развития

> Текущий статус: мы только фиксируем понимание и очередь экспериментов. Ни одно из перечисленных ниже изменений пока не реализовано. Имплементация начнётся только по отдельной команде.

## Главный рабочий цикл

Каждую новую тему проходим одинаково:

1. Понимаем проблему, смысл и механику.
2. Находим соответствующее место в текущем коде Tiny Manas.
3. Внедряем только одно изменение.
4. Сравниваем его с зафиксированной базовой моделью по качеству, скорости и памяти.
5. Записываем результат в `docs/RESEARCH_LOG.md` и оставляем изменение только при наличии пользы.

## Что уже разобрали и зафиксировали

### Проблема большого выходного слоя

Для батча `B = 12`, длины последовательности `T = 64` и словаря из 32 768 токенов LM Head создаёт:

```text
12 × 64 × 32 768 = 25 165 824 логита
```

Одна такая матрица занимает примерно 96 MiB в FP32 и 48 MiB в BF16. Кроме памяти, LM Head должен сравнить представление каждой из 768 позиций со всем словарём, поэтому выходной слой требует заметного количества вычислений.

Мы разобрали пять способов работы с этой проблемой:

- **BF16 mixed precision** уменьшает память отдельных тензоров и может ускорить вычисления, не меняя задачу модели;
- **Fused Linear Cross-Entropy / Cut Cross-Entropy** не хранит полную матрицу логитов и экономит в основном память, но подходящую реализацию ещё нужно отдельно проверить на MPS;
- **Adaptive Softmax** меняет плоский выходной слой на иерархический и пока не оправдан для словаря на 32 768 токенов;
- **Sampled Softmax** обучает модель на выборке кандидатов вместо полного словаря, приближает исходную задачу и пока нам не нужен;
- **логиты только для последней позиции** устраняют лишнюю работу LM Head во время генерации, но не применяются во время обучения, где полезна каждая позиция.

### Принятые решения

#### 1. Использовать BF16 mixed precision

Выбираем **BF16**, а не FP16. У BF16 столько же битов экспоненты, сколько у FP32, поэтому диапазон представимых значений остаётся почти таким же. Цена — меньшая точность мантиссы: число хранится менее подробно.

Мы не переводим вслепую абсолютно все вычисления в BF16. Планируем использовать mixed precision: подходящие матричные операции выполняются в BF16, а чувствительные операции и необходимые состояния остаются в FP32.

Перед принятием изменения нужно проверить:

- что используемые операции действительно выполняются на MPS без незаметного переноса на CPU;
- отсутствие `NaN`, `Inf` и нестабильного loss;
- пиковую память;
- токены в секунду и время шага;
- validation loss и качество генераций относительно базовой FP32-версии.

Статус: **понято и выбрано, не реализовано**.

#### 2. Считать LM Head только для последней позиции при генерации

Во время обучения сохраняем логиты для всех позиций: каждая из них даёт полезную пару «текущий токен → следующий токен».

Во время генерации нужен только следующий токен после конца исходного текста. Поэтому LM Head должен получать только последнее скрытое представление:

```text
полный путь:       (B, T, C) → (B, T, vocab_size)
путь генерации:    (B, T, C) → (B, C) → (B, vocab_size)
```

Проверяем:

- совпадает ли последний вектор логитов с результатом полного пути;
- совпадает ли генерация при одинаковом seed;
- насколько уменьшились время и пиковая память генерации.

Это изменение ускоряет только LM Head. Повторный расчёт самого Transformer позже будет устранять KV cache.

Статус: **понято и выбрано, не реализовано**.

#### 3. Сравнить словари 32k, 16k и 8k

Меньший словарь уменьшает таблицу эмбеддингов, LM Head, количество логитов и стоимость сравнения со всеми кандидатами. Но текст при этом может разбиваться на большее количество токенов, поэтому в фиксированное контекстное окно поместится меньше исходного текста.

Проводим отдельный контролируемый эксперимент:

```text
32 768 токенов — текущая базовая версия
16 384 токена
 8 192 токена
```

Для честного сравнения:

- обучаем три byte-level BPE токенайзера на одном и том же корпусе и с одинаковой обработкой текста;
- не меняем границы train, validation и test частей *Манаса*;
- сохраняем одинаковыми архитектуру Transformer и остальные настройки;
- обучаем модели на одинаковом количестве исходного текста, а не просто на одинаковом количестве токенов;
- записываем итоговое число параметров, потому что размер embedding/LM Head изменится;
- измеряем длину токенизированного корпуса, степень сжатия, память логитов, скорость обучения и генерации.

Обычную perplexity между разными токенайзерами напрямую не сравниваем: один «шанс выбора» соответствует разным кускам текста. Основной общей метрикой качества будет negative log-likelihood (NLL), нормализованный по одинаковым исходным UTF-8 байтам текста (`bits per byte`), вместе с человеческой проверкой генераций.

Статус: **понято и выбрано, не реализовано**.

## Очередь реализации после команды на старт

Изменения внедряем строго по одному:

1. **Логиты только для последней позиции при генерации.** Самое локальное изменение без влияния на обучение.
2. **BF16 mixed precision.** Сравниваем с неизменной базовой FP32-версией по стабильности, качеству, скорости и памяти.
3. **Токенайзеры 32k / 16k / 8k.** Отдельный более дорогой эксперимент, требующий повторной токенизации и обучения моделей.
4. **Fused или chunked Linear Cross-Entropy** рассматриваем только после измерения предыдущих шагов и только если выходной слой остаётся реальным ограничением памяти.

После каждого шага либо сохраняем доказанное улучшение, либо откатываем эксперимент и фиксируем отрицательный результат. Следующий шаг не смешиваем с предыдущим.

## Этап 1. Понять уже работающую тренировку

- правильная инициализация параметров;
- AdamW и weight decay;
- effective batch и gradient accumulation;
- warmup и cosine decay;
- gradient clipping.

На этом этапе архитектуру не меняем: сначала разбираем уже реализованный путь до уровня, на котором можем объяснить каждую строку и предсказать последствия изменения настройки.

## Этап 2. Модернизировать обучение и Transformer

Изучаем и сразу по одному внедряем:

1. BF16 mixed precision — решение уже принято, эксперимент описан выше;
2. `torch.compile` и kernel fusion;
3. activation checkpointing;
4. RoPE вместо обучаемых position embeddings;
5. RMSNorm вместо LayerNorm;
6. SwiGLU вместо GELU-FFN;
7. GQA вместо обычного multi-head attention.

Каждая замена — отдельный эксперимент. Ускорение считается успешным только по реальному замеру на MPS; более современный механизм сам по себе не считается улучшением.

## Этап 3. Ускорить инференс

1. логиты только для последней позиции — решение уже принято, эксперимент описан выше;
2. KV cache;
3. раздельные стадии prefill и decode;
4. batching нескольких запросов;
5. quantization весов;
6. FlashAttention или доступная на MPS эквивалентная оптимизация той же математики attention.

Цель этапа — измеримо уменьшить задержку, расход памяти и стоимость одного сгенерированного токена без скрытого ухудшения текста.

## Этап 4. Улучшить данные

- найти юридически пригодные версии *Манаса* от других сказителей;
- отделить целые документы для validation и test;
- проверить очистку, дубликаты, границы документов и качество токенизации;
- сравнивать новые наборы данных при неизменной архитектуре.

Это главный путь к более связной модели: увеличение числа параметров не заменит новые качественные тексты.

## Этап 5. Post-training

1. SFT на реальных, проверенных парах «инструкция → хороший ответ»;
2. сбор человеческих предпочтений между двумя ответами;
3. DPO как первый способ обучить модель на этих предпочтениях;
4. RLHF — только позже, если появится задача, для которой оправданы reward model и более сложное обучение.

Post-training не добавляет модели отсутствующие базовые знания. Он учит уже достаточно сильную базовую модель удобнее использовать то, что она выучила раньше.
