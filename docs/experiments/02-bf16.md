# 02 — BF16 mixed precision

Status: probe passed; full paired training in progress, not promoted. Date: 2026-09-04.

## Hypothesis and gates

On this actual M5/MPS/PyTorch 2.13 host, autocast may reduce activation/output
storage and improve step throughput while FP32 parameters, AdamW state and
cross-entropy preserve numerical stability. Do not convert the whole model.
Use `torch.autocast("mps", dtype=torch.bfloat16)` only around forward and loss;
backward and optimizer update run outside. No CPU fallback or FP16 substitution.

First run two fresh models with the same initialization seed, original 27M
configuration, same real training windows, dropout 0.2, optimizer/schedule and
accumulation. Only forward precision changes. 100 optimizer steps each, then
32 identical validation batches evaluated in FP32. Keep validation protected
from training; never read test. The 100-step cap is a stability/cost probe, not
an abbreviated substitute for the final matched training experiment.

Forecast: finite gradients/loss, validation loss within 0.1 nats, at least 5%
step-time reduction or 10% sampled activation-memory reduction. Falsifier:
unsupported operations, nonfinite values, adverse loss trend, or no worthwhile
resource gain. If the probe passes, compare full matched runs before promotion;
final validation degradation above 0.05 nats is unacceptable without a separately
approved tradeoff. Inspect raw generations for final accepted runs.

Record every step, synchronized time and live allocator samples after forward,
backward and update. Those samples are lower bounds, not true peak memory.
Warmup is excluded from reported median step time. No blanket 2x memory/speed
claim: optimizer state and parameters remain FP32. Cap MPS allocation at 65%
of its recommended budget on the 16 GB shared host.

Command: `.venv/bin/python scripts/experiment_bf16.py`.
Source: [PyTorch AMP documentation](https://docs.pytorch.org/docs/stable/amp.html).
Inspect actual output/loss/parameter/optimizer dtypes rather than assuming
every operation is autocast on the selected backend.

## Probe result

Run: `runs/optimization-02-bf16-20260904T052804Z`, source base `ab72944`;
runner preserved in `scripts/experiment_bf16.py`. All 100 optimizer steps per
mode completed with finite gradients. Seed 1337, B=8,T=256, accumulation=2;
probe sampler seed 1337, fixed validation sampler seed 9001 (32 batches).

| Measurement | FP32 | BF16 autocast |
|---|---:|---:|
| Median update seconds, excluding first 10 | 0.514812 | 0.352698 |
| Last 10 mean train loss | 7.095695 | 7.095904 |
| Identical-batch validation loss, FP32 evaluation | 7.135342 | 7.135239 |
| Maximum sampled allocated bytes | 2,298,147,072 | 2,250,727,168 |
| Maximum sampled driver bytes | 3,542,925,312 | 3,594,305,536 |

The BF16 probe had 31.5% lower median step latency (1.46x throughput ratio).
Validation difference was -0.000102 nats. Output dtype was BF16, while loss,
parameters and AdamW states were FP32. Memory did **not** halve: sampled live
allocation fell only 2.1%, and driver allocation increased 1.5%. The FP32
optimizer and full-vocabulary loss remain substantial costs.

This passes the speed/stability gate, not the final quality gate. Sequential
mode order and short warmup training limit the inference; the full comparison
must not reuse these probe weights as if they were trained models.

## Full comparison preregistration

Command: `.venv/bin/python scripts/run_bf16_comparison.py`.
Use the actual shared `train` implementation with one explicit config option,
`training.precision`. Default stays FP32 until acceptance. Autocast surrounds
training forward/loss only; evaluation and generation stay FP32 in both arms.

Two fresh 3000-step runs use original 27M settings and seeds, with early stopping
disabled **in both** arms so both receive 12,288,000 training target positions.
Unlike the probe, the shared training sampler uses the original seed+1 protocol.
Best checkpoint selection is still by scheduled validation loss every 100 steps.
After each run: 100 identical validation batches and the existing 20-sample
generation/memorization audit. Test is not used. No checkpoint is promoted yet.

Full-run gate: BF16 validation no worse than FP32 +0.05 nats; no new nonfinite
behavior or obvious raw-output degradation; >=5% useful throughput benefit.
Inspect all raw samples before accepting. Existing training memory fields sample
after updates, so do not equate them with the probe's within-step samples or a
true peak. Both artifacts preserve their measurement definition.
